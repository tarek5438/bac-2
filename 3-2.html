🧭 مدخل الدرس: كيف تنتقل الطلبات والاستجابات بين العميل والخادم؟

في الدرس 3-1 تعلمت أن الواجهة الأمامية والواجهة الخلفية تتعاونان لتنفيذ طلب المستخدم. عندما تنقر على رابط أو تبدأ بحثاً، يطلب المتصفح غالباً البيانات التي يحتاجها من خدمة على خادم عبر الشبكة. المتصفح هنا عميل (Client) يرسل طلباً، ويعيد الخادم (Server) استجابة. وتحدد بروتوكولات مثل HTTP / HTTPS قواعد هذا التبادل.

🎯 أهداف التعلم الرسمية (ص 56)

  • اشرح نموذج العميل والخادم ودورة الطلب والاستجابة.
  • ميّز بين HTTP وHTTPS، واستخدم GET وPOST في سياقات مناسبة.
  • فسّر رموز حالة HTTP الشائعة، واشرح دور API وJSON في تبادل البيانات.
  • صمّم طريقة اتصال مناسبة لمهمة في تطبيق ويب، وبرّر اختيارك.

⭐ الفكرة الأساسية والمفاهيم الخمسة (ص 57)

تعمل تطبيقات الويب من خلال إرسال العميل للطلبات وإرجاع الخادم للاستجابات، باستخدام بروتوكولات (HTTP/HTTPS) وغالباً واجهات برمجة تطبيقات (API) تتبادل البيانات بصيغ مثل JSON.

العميل / الخادم HTTP / HTTPS طريقة طلب HTTP رمز حالة HTTP API / JSON
📦تشبيه من الواقع: طلب توصيل وجبة أو طرد بريدي!

تخيل دورة الاتصال في الويب مثل طلب وجبة عبر الهاتف أو التطبيق:
1. أنت وهاتفك (العميل Client): الطرف الذي يبدأ بطلب الخدمة أو البيانات.
2. مركز الطلبات والمطعم (الخادم Server): الطرف الذي يستقبل الطلبات من العملاء، يعالجها، ويعيد الوجبة (الاستجابة).
3. نوع الطلب (GET مقابل POST): إذا اتصلت لتسأل «ما هي قائمة أسعار اليوم؟» فأنت تسترجع معلومات (GET)، أما إذا أرسلت «بيانات عنوانك وتفاصيل طلبك وبطاقة الدفع» ليتم تسجيلها ومعالجتها فأنت ترسل بيانات (POST).
4. إشعار حالة الطلب (رمز الحالة Status Code): الرقم 200 يعني «تم تجهيز طلبك بنجاح»، الرقم 404 يعني «الصنف الذي طلبته غير موجود في القائمة»، والرقم 500 يعني «حدث عطل داخلي طارئ في فرن المطعم منعه من إكمال الطلب»!

❓ السؤال الرئيسي للدرس (ص 57): كيف يتواصل العميل والخادم لتشغيل تطبيق الويب، وما القواعد والرسائل التي يستخدمانها؟
المحور الأول والثاني (كتاب ص 57 - 58)

🖥️ 1. العميل والخادم (Client & Server) وبروتوكولات HTTP و HTTPS

يُعد نموذج الطلب والاستجابة (Request-Response Model) أساسياً في كثير من تطبيقات الويب (الشكل 3.2.1 ص 57)، حيث يرسل العميل طلباً مثل «أرني هذه الصفحة»، ويعالج الخادم الطلب ويعيد استجابة تتضمن البيانات المطلوبة.

المفهوم / البروتوكول التعريف والدور الأساسي (كتاب ص 57 - 58) أمثلة وخصائص
العميل
(Client)		 الجانب الذي يطلب البيانات أو المعالجة؛ وهو برنامج أو جهاز يرسل طلباً إلى خدمة أخرى عبر الشبكة. متصفح الويب (Web Browser)، وتطبيق الهاتف المحمول.
الخادم
(Server)		 الجانب الذي يستقبل الطلبات من العملاء، ويعالجها، ويعيد الاستجابات المناسبة. خادم الويب (Web Server)، وخادم التطبيقات.
بروتوكول HTTP بروتوكول نقل النص التشعبي (Hypertext Transfer Protocol): بروتوكول يُستخدم لتبادل الرسائل بين عميل وخادم على الويب بدون تشفير. تبدأ عناوينه بـ http://؛ البيانات فيه غير مشفرة أثناء النقل.
بروتوكول HTTPS استخدام HTTP عبر اتصال TLS (Transport Layer Security) آمن. يساعد TLS على حماية سرية الاتصال وسلامته، وعلى مصادقة الخادم، بحيث لا يستطيع المتجسس قراءة المحتوى أو تعديله بسهولة أثناء النقل. تبدأ عناوينه بـ https://؛ ضروري لصفحات تسجيل الدخول والدفع والبيانات الحساسة.

المحور الثالث (كتاب ص 58)

📡 2. طلبات HTTP (GET و POST) ورموز حالة الاستجابة (200، 404، 500)

تتضمن الطلبات المرسلة من العميل إلى الخادم معلومات تسمى طريقة طلب HTTP (HTTP Request Method) توضح «نوع العملية المطلوبة». وتتضمن الاستجابات المرسلة من الخادم إلى العميل رقماً يشير إلى نتيجة المعالجة يسمى رمز حالة HTTP (HTTP Status Code).

📥 أولاً: طرق طلب HTTP الشائعة (ص 58)

الأسلوب الدور الأساسي أمثلة الكتاب المدرسي
GET يُستخدم عادةً لطلب مورد أو استرجاع بيانات من الخادم. عرض صفحة ويب، استرجاع نتائج البحث، تحميل سجل درجات.
POST يُستخدم عادةً لإرسال بيانات ليعالجها الخادم. إرسال معلومات تسجيل الدخول، إرسال محتويات نموذج تواصل.

📊 ثانياً: رموز حالة HTTP النموذجية (ص 58)

رمز الحالة المعنى الدقيق في المنهج (ص 58)
200 نجاح: تمت معالجة الطلب بنجاح وإعادة النتيجة.
404 غير موجود: المورد المطلوب غير موجود بهذا العنوان (مثل صفحة مفقودة أو رابط خطأ).
500 خطأ داخلي في الخادم: منعه من إكمال الطلب؛ ولا يحدد الرمز وحده السبب التفصيلي.

🧪 محاكي مختبر طلبات HTTP ورموز الحالة (اضغط لتجربة كل سيناريو عملي):

📡 طريقة الطلب: GET (استرجاع مورد/بيانات) ⬅️ رمز الحالة المُعاد: 200 OK
التفسير: العميل طلب استرجاع صفحة الويب، والخادم وجدها وعالج الطلب بنجاح وأعاد الصفحة للمتصفح (ص 58).
المحور الرابع (كتاب ص 58 و ص 60)

🧩 3. واجهة برمجة التطبيقات (API) وتنسيق البيانات (JSON)

لا يقتصر التواصل في الويب على طلب صفحات كاملة؛ بل تتبادل البرمجيات البيانات المنظمة مباشرة عبر واجهات برمجة التطبيقات (APIs) باستخدام صيغ نصية قياسية خفيفة مثل JSON.

🔌 واجهة برمجة التطبيقات (API)

Application Programming Interface: مجموعة قواعد واضحة (واجهة أو عقد محدد) تسمح لبرنامج بطلب بيانات أو وظائف من برنامج آخر.
• قد ترسل الواجهة الأمامية طلبات إلى خدمة خلفية عبر API وتستقبل منها البيانات.
• مثال من الكتاب (ص 60): طلب الجدول الدراسي لليوم من نظام مدرسة أخرى، أو خدمة طقس تعيد توقعات اليوم.

📄 صيغة بيانات JSON

JavaScript Object Notation: صيغة نصية شائعة وقابلة للقراءة لتمثيل وتبادل البيانات المهيكلة باستخدام كائنات (Objects) ومصفوفات (Arrays) وقيم بسيطة.
• أهم مميزاتها: خفيفة، سهلة القراءة للبشر والآلات، وتدعمها لغات وأدوات برمجية كثيرة.
• تتكون من أزواج: المفتاح (Key) ومقابله القيمة (Value).

🔬 محاكي قارئ ومحلل بيانات JSON التفاعلي (شامل نشاط الكتاب ص 60):

{ "city": "Cairo", "temperature": 31 }

🔍 تحليل أزواج المفتاح (Key) والقيمة (Value):

  • المفتاح الأول (Key 1): "city" ⬅️ القيمة المقابلة (Value): "Cairo" (نص).
  • المفتاح الثاني (Key 2): "temperature" ⬅️ القيمة المقابلة (Value): 31 (رقم).
  • طريقة الطلب المناسبة: GET عبر بروتوكول HTTPS.

📗 جميع أسئلة وأنشطة وتمارين الكتاب المدرسي محلولة بالتفصيل

💡 1. أنشطة «توقّف وفكّر» (ص 58 و ص 59) + «المثال المحلول» (ص 59)▼

توقّف وفكّر (ص 58): لماذا يجب أن تستخدم صفحة تسجيل الدخول HTTPS بدلاً من HTTP العادي؟
⬅️ الإجابة: لأن صفحة تسجيل الدخول ترسل بيانات حساسة (مثل اسم المستخدم وكلمة المرور)؛ ويوفر بروتوكول HTTPS عبر اتصال TLS آمن تشفير المحتوى لحماية سريته وسلامته ومصادقة الخادم، فلا يستطيع المتجسس قراءة كلمة المرور أو تعديلها أثناء النقل عبر الشبكة، على عكس HTTP العادي الذي ينقلها مكشوفة.

توقّف وفكّر (ص 59): إذا استقبل المتصفح رمز حالة HTTP 404، ماذا يجب أن يخبر المستخدم — وأي جانب كانت به المشكلة؟
⬅️ الإجابة: يجب أن يخبر المستخدم برسالة واضحة بأن «الصفحة أو المورد المطلوب غير موجود بهذا العنوان» (مع اقتراح العودة للصفحة الرئيسية أو التحقق من صحة الرابط). والجانب المرتبط بالمشكلة هو طلب العميل لعنوان غير موجود على الخادم (فئة أخطاء طلب العميل 4xx حيث لم يجد الخادم المورد في ذلك المسار).

المثال المحلول (ص 59):
(1) ضع علامة ○ أو ×:
• أ: ○ (وصف صحيح لأدوار العميل الذي يطلب البيانات والخادم الذي يعيد الاستجابة).
• ب: ○ (يستخدم HTTPS بروتوكول HTTP عبر اتصال محمي بـ TLS).
• جـ: × (يُستخدم GET عادةً لطلب مورد أو بيانات، ويُستخدم POST عادةً لإرسال بيانات إلى الخادم لمعالجتها؛ فالعبارة تعكس الاستخدام المعتاد).
• د: ○ (404 رمز حالة يشير إلى أن المورد المطلوب غير موجود، مثل صفحة مفقودة).
(2) المطابقة:
• 1: بروتوكول اتصال لتبادل البيانات بين متصفحات الويب والخوادم ⬅️ (أ) HTTP.
• 2: واجهة أو مجموعة قواعد محددة تتيح لبرنامج طلب بيانات أو وظائف من برنامج أو خدمة أخرى ⬅️ (ب) API.
• 3: بروتوكول اتصال يضيف تشفيراً إلى HTTP ⬅️ (جـ) HTTPS.

📝 2. سؤال الامتحان [6 درجات] (ص 59) + «تدرّب 1 و 2» (ص 59 - 60)▼

سؤال على نمط الامتحان [6 درجات] (ص 59): اشرح خطوة بخطوة ما يحدث عندما يطلب المتصفح صفحة ويب ويستجيب الخادم (أشر إلى: العميل، الطلب، طريقة طلب HTTP، الاستجابة، رمز حالة HTTP):
⬅️ الإجابة النموذجية:
1. يعمل المتصفح بوصفه العميل (Client)، فيقوم بإنشاء وإرسال طلب (Request) عبر الشبكة إلى الخادم.
2. يتضمن هذا الطلب طريقة طلب HTTP مناسبة وهي GET لأن الهدف هو استرجاع وعرض صفحة ويب من الخادم.
3. يستقبل الخادم (Server) الطلب ويعالجه، ثم يعيد استجابة (Response) إلى المتصفح تحتوي على محتوى الصفحة المطلوبة مرفقة بـ رمز حالة HTTP (مثل الرمز 200 الذي يدل على نجاح معالجة الطلب، أو 404 إذا لم تكن الصفحة موجودة).

حل تدرّب 1 (ص 59):
1) العميل (Client) | 2) الخادم (Server) | 3) HTTPS | 4) GET | 5) واجهة برمجة التطبيقات (API).

حل تدرّب 2 (ص 59 - 60):
(1) التركيبة غير المناسبة بين رمز حالة HTTP والمعنى هي: (جـ) 500 — تمت معالجة الطلب بنجاح (لأن 500 يعني خطأ داخلي في الخادم، بينما 200 هو رمز النجاح).
(2) الخيار الذي يصف واجهة برمجة التطبيقات (API) بأنسب شكل هو: (ب) نظام لتبادل البيانات بين برمجيات مختلفة.

⚙️ 3. حل «فكّر كمهندس» (ص 60) + «اقرأ البيانات JSON» (ص 60) + «طبّق ما تعلمته» (ص 60)▼

حل نشاط «فكّر كمهندس: ابحث ثم قرر» (تطبيق المدرسة ص 60):
1. اختيار الأسلوب:
• تحميل سجل درجات الطالب ⬅️ GET (لأنه استرجاع بيانات وعرض ملف من الخادم).
• إرسال نموذج تسجيل الدخول ⬅️ POST (لأنه إرسال بيانات سرية ليعالجها الخادم ويتحقق منها).
• طلب الجدول الدراسي لليوم من نظام مدرسة أخرى ⬅️ GET، ونعم تكون واجهة برمجة التطبيقات (API) متضمنة لأن النظام يطلب بيانات مهيكلة من برنامج/نظام مدرسة أخرى.
2. اختيار البروتوكول: يجب أن يستخدم تسجيل الدخول بروتوكول HTTPS؛ لحماية سرية بيانات الدخول (كلمة المرور) وسلامتها عبر تشفير TLS ومصادقة خادم المدرسة.
3. القرار: نوصي بـ ☑️ استخدام HTTPS والأسلوب المناسب لكل إجراء؛ لأن(1) HTTPS يحمي كلمات المرور ودرجات الطلاب من التنصت والتلاعب، و(2) التفرقة بين GET للاسترجاع وPOST للإرسال تضمن عمل التطبيق وفق القواعد القياسية السليمة للويب.

حل نشاط «اقرأ البيانات (JSON)» (ص 60):
في الكود: { "city": "Cairo", "temperature": 31 }:
• مثال1: المفتاح (Key) هو "city"، والقيمة المقابلة له (Value) هي "Cairo".
• مثال2: المفتاح (Key) هو "temperature"، والقيمة المقابلة له (Value) هي 31.

حل نشاط «طبّق ما تعلمته» - خدمة الطقس (ص 60):
• طريقة طلب HTTP: سيستخدم العميل أسلوب GET لأنه يطلب استرجاع بيانات توقعات الطقس من الخادم.
• لماذا تستخدم الخدمة HTTPS: لتأمين الاتصال عبر TLS، مما يضمن مصادقة خادم الطقس الحقيقي وعدم تلاعب أي طرف ثالث ببيانات الأرصاد أثناء النقل.
• ميزة واحدة لاستقبال البيانات بصيغة JSON: أنها صيغة نصية مهيكلة خفيفة وسهلة القراءة والفرز البرمجي، وتدعمها لغات وأدوات برمجية كثيرة لعرض درجات الحرارة فوراً في التطبيق.

🏆 4. إجابة السؤال الرئيسي + حل تمارين نهاية الدرس + «فكّر وتحدَّ نفسك» (ص 61)▼

إجابة السؤال الرئيسي (ص 61): في كثير من الحالات يرسل العميل طلباً ويعيد الخادم استجابة وفق قواعد HTTP، وقد تستخدم التطبيقات وسائل أخرى عند الحاجة. يحدد HTTP طريقة تبادل الرسائل، ويستخدم HTTPS اتصال TLS آمناً. وتوضح طريقة HTTP الغرض من الطلب؛ فيُستخدم GET عادةً لطلب مورد أو بيانات، وPOST لإرسال بيانات ليعالجها الخادم. وتبين رموز الحالة نتيجة معالجة الطلب. وقد تستخدم التطبيقات واجهة برمجة تطبيقات (API) وقواعد واضحة لتبادل البيانات، وربما تمثلها بصيغة JSON النصية المهيكلة.

حل تمارين نهاية الدرس (ص 61):
• سؤال 2 (إكمال الفقرة): (1) العميل | (2) الخادم | (3) HTTP | (4) HTTPS.
• سؤال 3-(1) (تحديد طريقة طلب HTTP: أ GET، ب POST):
1 عرض صفحة ويب ⬅️ أ (GET)
2 إدخال معرّف وكلمة مرور في نموذج تسجيل الدخول وإرسالهما ⬅️ ب (POST)
3 عرض نتائج البحث ⬅️ أ (GET)
4 إرسال محتويات نموذج التواصل ⬅️ ب (POST)
• سؤال 3-(2) (اختيار من متعدد): الخيار الذي يصف HTTPS بأنسب شكل هو (جـ) بروتوكول يستخدم HTTP عبر اتصال محمي بـ TLS.

فكر وتحدَّ نفسك (ص 61):
• تأمّل: عندما تفشل صفحة في التحميل، أي رمز حالة سيساعدك أكثر على فهم السبب، وماذا سيخبرك؟ ⬅️ التمييز بين الرمز 404 (يخبرني أن الرابط الذي كتبته خطأ أو الصفحة حُذفت من الموقع) والرمز 500 (يخبرني أن الرابط صحيح ولكن خادم الموقع نفسه يواجه عطلاً داخلياً منعه من إتمام الطلب).
• تحدٍّ: اذكر تطبيقاً واحداً تستخدمه وصف طلباً واحداً يرسله والاستجابة التي يتوقعها ⬅️ في تطبيق متجر إلكتروني: يرسل التطبيق طلب GET عبر HTTPS لاستعراض تفاصيل منتج، ويتوقع استجابة برمز حالة 200 محملة ببيانات المنتج وسعره بصيغة JSON.
• الخلاصة: تذكّر أن: العميل يطلب، والخادم يستجيب — عبر HTTP/HTTPS، بأسلوب (GET/POST)، ورمز حالة، وغالباً واجهة برمجة تطبيقات تعيد بيانات JSON.
